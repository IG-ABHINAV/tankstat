# Photo reading (a vision model fills the forms)

## Photo reading

- Photo reading in the app (`Domain/Recognition`, `Application/Recognition`, `Infrastructure/Recognition`; optional, off by default): photos picked in the add dialogs (refueling, expense, recurring "done") are uploaded as drafts with `?form=refueling|expense&locale=xx`; photos added to a saved log in its edit dialog go to `PUT /media/expenses|refuelings/{logId}/photos` with the same query and are queued by `RecognitionService.QueueForLogPhotoAsync` (only the uploader's photo of that log; hints from the log, not the vehicle today: the odometer before the log's day via `OdometerService.PreviousAsync`, the log's own currency); `LogPhotoInfo.reading` (batched by `PhotoReadingsLoader`) gives the edit dialog its readings; with a form, `RecognitionService.QueueForDraftAsync` queues a `PhotoReading` (id = the image id; the purpose decides the allowed kinds; the hints Locale/LastOdometer/Currency/Today are taken right then because the worker has no user). Queueing never fails the upload. `RecognitionWorker` (one of the app's three background jobs, with `PasswordResetMailer` and `BackupWorker`; registered always, returns at once when not set up) wakes on `IRecognitionSignal` or every 10 s; `PhotoReadingProcessor` claims due readings atomically (repository `ExecuteUpdate`), claims nothing while the provider is unavailable (`RecognitionAvailability`, 30 s cache), retries unavailable providers (5 attempts, 10 s x 3^n), fails refused photos, requeues attempts cut short by a restart (stale after 5 min, or longer than `Recognition:OpenAiCompatible:TimeoutSeconds` + 1 min: `PhotoReadingProcessor.StaleAfter(options)`) and normalises values with `ReadingNormaliser` (a blank beats a wrong value). Values are a JSON column; the table has a cascading foreign key to `Images`, so a reading goes with its picture on every path. `RecognitionOptions` are bound but never validated on start: `RecognitionSetup` turns unusable settings (even unbindable ones) into "off" plus a warning logged by the worker; never let a recognition setting stop the app. The provider is `OpenAiCompatibleRecognitionProvider`, over a named HttpClient without a timeout of its own, for any OpenAI-compatible chat completions API (`Recognition:OpenAiCompatible:*`: `BaseUrl` including `/v1`, `Model` required, `ApiKey` optional as a Bearer token, `SystemPrompt`/`SystemPromptFile` replacing `OpenAiCompatiblePrompt.DefaultSystemPrompt` (printed in `docs/photo-reading.md`, pinned by a test) while the contract (allowed kinds and fields, formats, locale conventions, JSON schema per `ResponseFormat`) is always sent and the latest odometer, currency and today never are; answers are read tolerantly (think blocks, code fences, text parts), a refusal is Rejected, non-JSON is Unavailable, and the values go through the pure `ReadingChecks.Check` in Application (fields per kind (a fuel receipt's `discount` since #204: a positive amount, a printed minus sign dropped by `ReadingNormaliser`, a 0 left out without a reason, `IsNoDiscount`), odometer window against `LastOdometer`, litres × price − discount ≈ total (`CrossChecked`: within `Loose` 1.5 % without a discount read, `Tight` 0.2 % with one, since a discount the total already lacks would fit the loose bar; when litres × price alone fits, only the discount is doubted, when nothing fits volume, price and discount are, the total stays), date window, ranges; the model's confidence only ever lowers the result; it returns `CheckedValues(Kept, Issues)`: every drop or doubt carries a `ReadingIssue(Field?, ReadingIssueCode)` from `Domain/Recognition/ReadingIssue.cs`, codes only, never the value, and the provider adds `Unrecognised`/`NothingLegible`; a missing rating reaches the checks as NaN and becomes `NoConfidence`); exception messages carry a status and a snake_case code at most, never server or model text; fixtures in `tests/backend/contracts/openai-compatible`), `NullRecognitionProvider` otherwise. A cloud `BaseUrl` is the operator's explicit choice (it sends photos off-site). The photo's trail is in the log at Debug, tied together by the reading's id (`RecognitionRequest.ReadingId`, set by the processor, never sent to the model): the provider's "Asking {Model} at {Server} to read photo {PhotoId}" and "{Model} answered photo ... said {Said}, listed {Listed}, kept [Field@confidence], issues [Field:Code]" (or "did not read photo ... after {ElapsedMs} ms"), then the worker's "Read photo {Id}: it shows {Kind}, {Sure} of {Values} values are sure enough" (`ProcessedReading.Summary`; `RecognitionSetup.IsSureEnough` is the one rule for what is sure enough, shared by `UsableValues` and `LogPhotoFiller`); at start the worker says at Information which model and server (`ServerAddress.Of`: no user info or query) and where the system prompt comes from, never its text (`RecognitionSetup.SystemPromptSetting`). `docs/photo-reading.md` prints the full request (system prompt, contracts for both dialogs, schema), pinned to the code by `OpenAiCompatiblePromptTests`. `Recognition:OpenAiCompatible:LogTraffic` (default off; the worker warns at start while on) puts `OpenAiTrafficHandler`, a `DelegatingHandler`, to work in the named client's pipeline: every request and answer (also the health check) is written at Information, one entry each, pretty-printed, numbered so the two pair up, with prompts and what the model read in them: the one place the app logs those, so keep it that way (the photo only as its size, the key masked in the header and wherever a server echoes it, bodies cut at 16 000 characters, a server's text escaped so only the layout breaks lines); the provider hands it the photo through `HttpRequestOptions` (`OpenAiTrafficHandler.Photo`). Drafts picked for reading are uploaded as JPEG while the server says reading is on (`usePhotoQueue` asks `recognitionStatus`, the dialog's own question; `resizeImage` `format: 'jpeg'`), since not every model server decodes WebP; `RecognitionNames` holds the kind and field names the prompt and the answer share. GraphQL: `recognitionStatus { available }` and `photoDrafts(ids)` (own drafts only; `UsableValues`: confidence >= `MinConfidence`, hints left out); `markRecurringExpensesDone` takes `photoIds`. Logs never contain read values.
- Logs saved before their photos are read (`Domain/Vehicles/LogReview.cs`): a refuelling may be saved without odometer, volume or total, an expense without amount (its odometer is optional anyway), but only while one of its photos is still being read (`LogPhotoFiller.MayWaitForDraftsAsync`: queued/reading, or uploaded less than `JustRead` ago; updates: `MayWaitForLogPhotosAsync`, a reading of one of its photos that is pending or was just read, the same window); otherwise `log.valuesRequired`. So `Refueling.OdometerReadingId`/`CostId`/`Volume` and `Expense.CostId` are nullable (no row until known; `Update` returns `LinkedChanges` for the repository, which saves the log first and deletes the let-go reading/cost in a second save of one transaction (`LinkedChangesExtensions.SaveLogAsync`: EF never saw the log point at them, so one save could delete a row the log still refers to)). `ReviewState`: AwaitingPhotos -> NeedsReview (values filled, `FilledFromPhoto` flags) / Incomplete (still missing) / None; a person's full save sets None (and marks the log's `LogReview` notifications read). `LogPhotoFiller.FillAsync` (no user) fills only empty values with sure values (like `UsableValues`; the discount only with the cost the photo creates, flagged `LogValues.Discount` (GraphQL `LogValue.DISCOUNT`, the edit dialog's `FROM_PHOTO`; never a waiting value, `WAITS_FOR`), never onto a cost a person entered, whose empty discount is theirs; the currency only ever comes from a photo, never from the reading's hint: a total without a legible currency is left empty, so the log stays incomplete for the person, instead of a foreign receipt being stored in the vehicle's usual currency), never checks odometer neighbours (user decision: the review catches it), recalculates consumption, logs a Debug line with ids and the names of the values (never what was read) and notifies the creator (`LogFilledFromPhoto`/`LogNotFilled`, derived, topic `LogReview`, subject `Refueling`/`Expense`). It runs after `LogAsync`/`AddAsync` attach the drafts, after an update that leaves the log waiting (a reading may have finished before the save), after a restore, and from `PhotoReadingProcessor` once per log after a round, for readings that finished (Read/Failed) of photos that belong to a log. Stats leave out logs still missing values; `ConsumptionCalculator` makes an interval with an unknown volume/odometer unknown. UI: in the add dialogs those fields stop being required while `drafts.pending` is non-empty (`ReadNote` `waiting`), grids show `ReviewBadge` in the date column and poll (`ServerGrid` `pollWhile`) while a row awaits its photos, edit dialogs show `ReviewCallout` and mark `filledFromPhoto` fields. The recurring "done" dialog has no required amount: an expense is logged exactly when an amount is given or a picked photo is still being read (`ReadNote` `waiting` on the amount); otherwise its photos are not sent and are deleted on close (`recurring.photosNotKept`). Frontend (`recognition/`): `useDraftReadings(uploads, enabled, log?)` (drafts, or with `log` the photos added to that saved log in this dialog session, asked with `fetchPolicy: 'no-cache'` because the answer holds photos without urls; status on open and, while it reads "off", again every 3 s for a minute after each upload; polls every 1.5 s while readings are pending, at most `READING_WAIT_MS` (110 s, just under the server's `JustRead`, so the dialog never offers to save while the server would refuse) after each upload), the pure fill rules in `readValues.ts` (fill fields the user has not changed, starting values count as unchanged, and fields left empty; offer, never overwrite, what they typed; an edit dialog's saved values are `kept`: only offered while not empty, kept apart from `touched`), `useReadFill` (controlled fillable fields), `ReadNote` in `Field`'s `extra` slot ("Read from the photo" / "The photo shows X · Use it"), a `role="status"` announcement, "Reading…" under thumbnails. Tests: `src/frontend/tankstat-react/tests/support/server.ts` answers `RecognitionStatus` with unavailable by default; use `fakeRecognition` from `mocks.tsx` to turn it on.
- Refuelling amounts: the refuelling dialog has a unit price field that is never saved (the server keeps computing `pricePerUnit`); volume, unit price and total follow each other through `keepAmountsInStep` (`src/frontend/tankstat-react/src/refuelingAmounts.ts`, pure): after a change, another amount is worked out in a fixed order: a calculated one first (it says nothing of its own), then the unit price (never saved: with a discount on the receipt it becomes the price paid per litre), then the total (never one the user typed or a photo read: the receipt's amount stays and the price shown is the pump's; a saved total in the edit dialog still follows a typed price), then the discount (volume × unit price − total, once the three are there; never below nothing: a pump price under the price paid per litre empties a worked-out discount and moves nothing else; and never the receipt's rounding: a difference under `ROUNDING_SHARE`, 0.1 % of the pump's amount, is not a discount; the user chose it so that a card's 2 Ft/L stays visible while rounding to whole or five forints does not show), and the volume only while it is empty, since the consumption comes from it and litres worked out from an amount paid and a pump price are wrong by any discount (#204: a volume with a value, typed, read from a photo or saved, never gives way); a change that is not the user's (a photo, the starting values) never moves a typed one, and a calculated amount that can no longer be worked out is emptied. It runs as `useReadFill`'s generic `keepInStep` hook (after typing, "Use", a photo and on the starting values); `FillState` keeps the `touched` and the `calculated` fields (`calculateField`/`clearCalculated`), where a photo only offers its value. A calculated amount is worked out again before any other, and gets no reason why a photo did not give it; `problemsToTell` tells a reason about several values (`AMOUNTS_DO_NOT_ADD`) once.
- Why a photo gave less than it might have (`Domain/Recognition/ReadingIssue.cs`, `recognition/readingIssues.ts`): the reasons are kept with the reading (`PhotoReading.Issues`, a JSON column of `ReadingIssue`s, codes only: `Complete(..., issues)`, which also says `Unrecognised` for a kind the dialog does not take), `RecognitionService.IssuesOf` adds the derived `Unsure` (a kept value under `MinConfidence` that no stored reason explains) and GraphQL has `PhotoReadingInfo.issues { code field }`; the add dialogs word them (`recognition/readingIssues.ts`: `mergeIssues` per dialog, `problemsToTell`: a reason about a field the dialog has and no photo filled, one per field, a whole-photo reason only when nothing was filled; `useDraftReadings.explanation`, `useReadFill` `problems` and its `last`, the vehicle's latest reading already formatted; `ReadingProblems` inside the `role="status"` region; texts `reading.issues.<CODE>` in English and Hungarian). A new reason = an enum value in `ReadingIssueCode` + where it arises + the text + the table in `docs/photo-reading.md`.
