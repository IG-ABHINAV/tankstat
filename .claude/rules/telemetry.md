# Telemetry (OpenTelemetry over OTLP)

- **Opt-in (#214):** traces, metrics and logs through one `UseOtlpExporter()` (it honours a signal's own `OTEL_EXPORTER_OTLP_{TRACES,METRICS,LOGS}_ENDPOINT`; `AddOtlpExporter()` does not, verified), registered by `Api/Telemetry/TelemetryExtensions.AddTelemetry` from `Program.cs` before `Build()`, never for `backup`/`decrypt`/`restore`/`schema export`, and only when `Application/Telemetry/TelemetryGate` (pure, never throws: telemetry never stops a start; it reads no file: whether a certificate named is there is a function its caller passes, `File.Exists` from the start, `IFileProbe` from the Server settings page's `SystemSettingsService` through `SettingsCatalog.Validate`, #312) says `On`: `OTEL_EXPORTER_OTLP_ENDPOINT` is the only switch (a signal's own endpoint alone is `SignalEndpointWithoutBase`, off: the other signals would go to the SDK's `localhost:4317`), `OTEL_SDK_DISABLED=true` is `Disabled`, and an endpoint that is not an absolute http(s) URI, a protocol other than exactly `grpc`/`http/protobuf` (the SDK compares as written) or headers that are not `key=value` pairs after URL-decoding, name a key twice or `User-Agent` (the exporter adds them to a dictionary, then its own User-Agent: it throws), a `_TIMEOUT` or `OTEL_METRIC_EXPORT_INTERVAL` of 0 (digits only, as the SDK parses; a non-number it ignores) or a `_CERTIFICATE`/`_CLIENT_CERTIFICATE`/`_CLIENT_KEY` file that is not there are `Misconfigured`, base and per-signal keys alike (`OtelSettings.CheckedKeys`, one rule `OtelSettings.ProblemOf(key, value)` by key suffix, shared with the Server settings page's `Validate`, so the wording is one). Without an endpoint nothing is registered (no provider, no HotChocolate listener, no OpenTelemetry logger). `Api/Telemetry/TelemetryReporter` (hosted) says what became of it: Information when on (protocol, signals, service name, never the endpoint or headers), Warning for the problems (named by setting, never by value), the per-signal endpoint alone and `Telemetry:TraceDatabase` set but without effect or not a bool, Debug when simply off; and a Warning at every start while database spans are on. While on, it also ends the export at `ApplicationStopped`: the three providers' `Shutdown(TelemetryReporter.ShutdownMs)` together (2 s), since the host's disposal would shut them down one after the other, each waiting its own 5 s on a collector that accepts and never answers.
- **Settings:** the SDK's own `OTEL_*` keys, which it reads from the host's `IConfiguration` (environment, the settings file and the Server settings page alike, verified), plus our `Telemetry:TraceDatabase` (`Application/Telemetry/TelemetryOptions`). The settings catalog's `Telemetry` group (read at start, *Restart needed*) edits `OTEL_EXPORTER_OTLP_ENDPOINT`, `_PROTOCOL` (a choice, words `systemSettings.choices.otlpProtocol`), `_HEADERS` (a secret, the fourth) and `OTEL_SERVICE_NAME` under those very names (exempt from the options-class pin like Logging's framework keys; built-in defaults `grpc` and `tankstat` from `OtelSettings.DefaultOf`), and `Telemetry:TraceDatabase` (pinned to `TelemetryOptions` in `OptionsSections`); `SettingsCatalog.Validate` checks every shape with the gate's own `OtelSettings.ProblemOf`, `Problems` skips the group (never fatal, like photo reading); the page greys the other four out while the endpoint is empty (`settingsRelevance.ts`, the gate's own rule). The per-signal keys, `OTEL_SDK_DISABLED`, `OTEL_RESOURCE_ATTRIBUTES` and the rest are environment only. `service.name` is set by the app (`OTEL_SERVICE_NAME` or `tankstat`), `service.version` is `HealthReporter.AppVersion`, and `AddEnvironmentVariableDetector()` comes after `AddService` in `ConfigureResource`, so `OTEL_RESOURCE_ATTRIBUTES` (an orchestrator's `service.instance.id`, a `service.name`) wins over the app's own where it says otherwise.
- **What is exported keeps the log's promise** (`logging.md`): the instrumentations are ASP.NET Core, HttpClient, HotChocolate (`HotChocolate.Diagnostics`, the version of `HotChocolate.AspNetCore`) and, behind `Telemetry:TraceDatabase`, EF Core (`OpenTelemetry.Instrumentation.EntityFrameworkCore`, a beta, at least 1.20.0-beta.1: no exception message in the span); meters ASP.NET Core's, HttpClient's, `System.Runtime`, `Microsoft.EntityFrameworkCore`; logs with `IncludeScopes` and `IncludeFormattedMessage`. HotChocolate (`builder.Services.AddGraphQL()`, which adds no server defaults, reaches the default schema Program.cs's `AddGraphQLServer()` chain configures): `RequestDetails = None` (never the request's JSON: variables, document, extensions, and neither its `operationName` nor a persisted-query hash, which the HTTP span copied as typed; the operation span names the operation from the parsed document), `IncludeDocument`/`IncludeDataLoaderKeys`/`IncludeOperationNameInSpanName` false, `MaxErrorEvents = 0` (an error event carries the message, and keyed messages quote typed values: only `graphql.error.count`), no `ResolveFieldValue` scope (a field span carries the client's alias) and no `ParseHttpRequest`/`ExecuteHttpRequest` scope (their parse and Accept-header errors are events with the client's text, which `MaxErrorEvents` does not cap). `ClientValueRedaction` (a span processor added in `WithTracing`, so before the exporter `UseOtlpExporter` adds; the tests' in-memory exporter, registered later still, gets the redacted spans) removes `user_agent.original`, every `db.query.parameter.*` (which `OTEL_SEMCONV_STABILITY_OPT_IN=database` with `OTEL_DOTNET_EXPERIMENTAL_EFCORE_ENABLE_TRACE_DB_QUERY_PARAMETERS=true` add) and `graphql.document.hash`/`.id` (a client's persisted-query id when no document is sent), redacts every value of `url.query` and of `url.full`'s query to `Redacted` itself (the ASP.NET Core and HttpClient instrumentations do so by default, but their `OTEL_DOTNET_EXPERIMENTAL_*_DISABLE_URL_QUERY_REDACTION` switches are read from the whole configuration, so the app does not rely on them), and leaves every HotChocolate span with an `exception` event unrecorded (`ActivityTraceFlags.Recorded` off, which every exporter honours), a client's fault (an operation name the document lacks) and the server's own (a resolver's exception, the database gone) alike: the exception's text can quote the request and an event cannot be taken off a span; the request's server span and the app's own Error line still record it. A client's `operationName` that is a valid GraphQL name is logged by `GraphQLLoggingListener` (`logging.md` blesses it: bounded identifier) and so exported, which is why the canary has a space. The one-time code's two lines log under their own categories, `OneTimeCode.SetupLine` and `OneTimeCode.RestoreLine` (below `OneTimeCode.LogCategory`), which `AddTelemetry` keeps out of the `OpenTelemetryLoggerProvider` in a `PostConfigure<LoggerFilterOptions>` (`TelemetryExtensions.KeepTheExportersPromises`, after the configuration's rules, again on a reload): a rule for a provider outranks every general one and a longer category a shorter, so the exporter's own rules that would match a code category (`*` included) are dropped and the three `None` rules added last, and the exporter's rules under `Microsoft.AspNetCore` below `SettingsCatalog.LogLevelFloor` are raised to it with a `Microsoft.AspNetCore`=Warning rule of the provider's own added (`Logging:OpenTelemetry:LogLevel:Default=Information` would otherwise export the request lines with the reset links' tokens). Never add the database providers' own sources (`Npgsql`, the MySQL connector's): they would trace the commands again past the switch. Metric attributes never carry ids. The accepted edge, documented: the log's, plus `url.path` and `server.address` (the Host header) on request spans, (a provider level of the exporter's own below Warning is raised by that `PostConfigure`, so it is no edge any more).
- **The app's own spans and metrics** (#219): `Application/Telemetry/AppTraces` (`ActivitySource` `Tankstat`, `System.Diagnostics` only, so any layer starts one; `AddSource` in `TelemetryExtensions`) and `AppMetrics` (meter `Tankstat` through the host's `IMeterFactory`, a meter of its own without one, which keeps a test's measurements apart; registered by `AddApplication` and `AddInfrastructure`, `TryAdd`; histograms carry their buckets as `InstrumentAdvice`). Names `tankstat.<area>.<verb>`, tags `tankstat.<area>.<what>`: ids, counts, outcomes and kinds, never a value or a message; a failure is `activity.Failed(key)` or, in an exception filter, `when (activity.FailedBy(e, ct))` (the key of a `KeyedException`, else its type; a cancellation, or anything thrown once `ct` asked to stop, is no failure, as `BackupRunner` holds), never `AddException` (an app's message quotes values); metric attributes are small sets (outcome, kind, trigger), never ids. Work no request carries is a root span of its own, `AppTraces.StartJob` (with a listener it clears `Activity.Current`, which `Task.Run` carries, and links the caller's span instead; without one it changes nothing): a backup run (`BackupRunner`: trigger, outcome; `tankstat.backup.duration`/`size`), its write (`BackupWriter`, a child of whatever asked: the run, the migrations), the restore at start (`RestoreStep.ApplyWaitingAsync`, only with a marker), the migrations at start (`DatabaseMigrator.MigrateAsync`, only with some pending), a photo read (`PhotoReadingProcessor`, per claimed reading, never per sweep; `tankstat.photo_reading.duration`). Inside a request a child span (`AppTraces.Source.StartActivity`): a sync batch and a span per change applied (`SyncService`; a parked one failed by its reason's key; `tankstat.sync.changes`). The providers start before the app's hosted services (OpenTelemetry's own runs first, so the start's spans are kept), but a restore applied before the host starts (`Program.cs`) needs `StartBeforeHost()` first (a smoke test fails without it). Tests: `AppTelemetryTests` (Application: `TestSupport/CapturedSpans`, which hears every test's spans, so a test finds its own by an id it made, and `CapturedMeasurements` on the `World`'s own meter), `TelemetryTests` (a Back up now run linked to its request, a refused restore at start, the migrations of a new database, a sync batch in the canary flow), `RestartSmokeTests` (a restore before the host starts reaches `OtlpReceiver`, a collector that keeps the raw OTLP/HTTP bodies: protobuf keeps a span's name as UTF-8).
- **Tests:** `TelemetryGateTests` (Application: the gate's table), `SettingsCatalogTests` (the group, shapes, defaults, the fourth secret), `TelemetryTests` (Api integration, a collection of its own with `DisableParallelization = true`, since ActivitySource and logger listeners are the process's: other hosts' spans would land in its exporter): a host with an endpoint nothing listens on (`http://127.0.0.1:1`, refused at once) and in-memory exporters added with `ConfigureOpenTelemetry{Tracer,Logger,Meter}Provider`; the canary flow of #214 (a plate, a name, a note with a quote and a backslash, an odometer refusal, a schedule's title in a refusal, a reset token as a variable and in the query, an alias, `extensions`, a User-Agent) with and without database spans (then with both EF opt-ins set), searched with `CapturedLog.Holds` in every span name, status, tag, event tag and exported log record; the one-time codes (mode None, a waiting setup, and a configured rule for the exact category) never exported; a request as one trace with its log lines; settings that cannot be used. `Program.cs` decides before the host is built, where a `TestApp`'s in-memory settings do not exist yet, so `TestApp` passes every `OTEL_*`/`Telemetry:*` key as a command-line argument (`UseSetting`), an empty one for each the developer's environment sets; `ApiFixture` clears such variables, `AppProcess` and the scripts drop them, and `SeederAppTests` (the one other host built under `WebApplicationFactory`) blanks them the same way through `TestSupport/TelemetryKeys.InEnvironment` (`ci-and-tests.md`). Also tested: the exporter's own log rules against the floor and the code (a wildcard rule more specific than the exact name), the redaction with both query-redaction switches set, the resource with `OTEL_RESOURCE_ATTRIBUTES`, a GraphQL span with an exception event, and the gate's new keys. Not covered in process: the Kestrel meter (TestServer has none) and the in-process restart, which the smoke tests start for real.
